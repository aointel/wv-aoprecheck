--------------------------------------------------------------------------------
HOW THE DATABASE DECIDES WHERE THE CALL GOES (THE TWO CHECKS)
--------------------------------------------------------------------------------
Every inbound 609 call is checked against our DB in two places:

1) WHEN THE CALL HITS /incomingcall (server/routes.ts handleIncomingCall)
   - We take Twilio "From" (caller phone), strip to last 10 digits.
   - DB: supabaseAdmin.from('masterlead')
         .select('id, state, taalk_market, first_name, last_name, taalk_lead_id, email, cn_email')
         .ilike('phone', '%' + callerLast10 + '%')
         .order('updated_at', { ascending: false })
         .limit(1)
         .maybeSingle()
   - That row gives us: market (taalk_market), state, lead name, lead_id, etc.
   - We build task attributes with buildTaskAttributesForEnqueue({ market: leadMarket, state: leadState, ... })
     and return <Enqueue><Task>...</Task></Enqueue>. So "where the call goes" (market/state) is
     determined by OUR DATABASE (masterlead) from the caller's phone number.
   - If no row found: we still enqueue with market='Unknown', state='XX'.

2) WHO CAN TAKE IT — WORKER ATTRIBUTES FROM OUR DB (customers)
   - When an agent goes online: POST /api/agents/voice-online (routes.ts) loads
     supabaseAdmin.from('customers').select('market, states, associate_id, first_name, last_name')
     .eq('company_email', email) or .eq('personal_email', email).
   - That customer row is passed to setWorkerAvailableForVoice(email, customer) →
     buildWorkerAttributesForVoice() → markets[] and licensed_states[] from customer.
   - syncWorker() writes those to the Twilio Worker. So "who is eligible" is from OUR
     DATABASE (customers) — market and states columns.
   - Bulk sync: sync-taskrouter-workers.ts does the same (reads customers, syncs Workers).

3) MATCHING (assignment callback)
   - When TaskRouter offers a task to a worker, we get task_attributes (market, state from
     masterlead) and worker_attributes (markets, licensed_states from customers).
   - We reject if task market not in worker.markets or task state not in worker.licensed_states.
   - So: call routing is 100% driven by masterlead (caller → task) and customers (agent →
     worker). No routing decision happens without our DB.

--------------------------------------------------------------------------------
LEAD DATA + ROUTING: CROSS-REF INCOMING PHONE WITH MASTERLEAD
--------------------------------------------------------------------------------
/incomingcall looks up the caller by From (incoming phone) in masterlead:
  masterlead ilike phone %last10, order updated_at desc, limit 1.
Task attributes then include: lead_id, market (taalk_market), state, lead_name,
first_name, last_name, taalk_lead_id, lead_email, routing_target (inbound609).
So lead and routing info move with the task to the assignment callback and UI.

--------------------------------------------------------------------------------
WORKER ATTRIBUTES (STATE & MARKETS) — HOW TASKROUTER KNOWS WHERE CALLS CAN GO
--------------------------------------------------------------------------------
TaskRouter routes by matching TASK attributes (market, state from the lead) to WORKER
attributes (markets, licensed_states from the agent/customer).

Where worker attributes come from:
- customers table: market (single or array), states (array or string). Synced into
  TaskRouter when workers are created/updated.
- sync-taskrouter-workers.ts: reads customers (market, states), builds Worker attrs
  via buildWorkerAttributesForVoice(email, customer) → markets[], licensed_states[].
- voice-online (POST /api/agents/voice-online): when an agent goes online we fetch
  their customer row by company_email/personal_email (market, states, associate_id,
  first_name, last_name) and pass it to setWorkerAvailableForVoice(email, customer).
  So the Worker in TaskRouter gets that agent's markets and licensed_states.

TaskRouter service: parseMarketFromCustomer(c) → string[], parseStatesFromCustomer(c)
→ string[]; buildWorkerAttributesForVoice(agentEmail, customer) sets
attrs.markets and attrs.licensed_states (or defaults to markets: ['Unknown'] if no
customer). syncWorker() writes these to the Twilio Worker.

Routing use:
- Assignment callback (POST /api/twilio/taskrouter/assignment): before returning
  dequeue, we check task market/state vs worker markets/licensed_states. If the task
  has a market and the worker's markets list is non-empty and does not include that
  market, we return instruction "reject" so TaskRouter offers to the next worker.
  Same for state vs licensed_states. So only workers whose markets include the task's
  market and whose licensed_states include the task's state get the call (or workers
  with no markets/states set accept any).

--------------------------------------------------------------------------------
INBOUND CALL LOOKUP → AGENT DISPLAY (FULL DATA FLOW)
--------------------------------------------------------------------------------
1) LOOKUP WHEN CALL COMES IN (server/routes.ts handleIncomingCall)
   - Twilio POSTs to /incomingcall with From (caller phone).
   - We take From, strip to last 10 digits: callerLast10.
   - DB: supabaseAdmin.from('masterlead')
         .select('id, state, taalk_market, first_name, last_name, taalk_lead_id, email, cn_email')
         .ilike('phone', '%' + callerLast10 + '%')
         .order('updated_at', { ascending: false })
         .limit(1)
         .maybeSingle()
   - One row: we set leadMarket (taalk_market), leadState (state), leadName (first_name + last_name),
     leadId, firstName, lastName, taalkLeadId, leadEmail. If no row: market='Unknown', state='XX'.

2) TASK ATTRIBUTES (same handler)
   - buildTaskAttributesForEnqueue({ call_sid, lead_id, market: leadMarket, state: leadState,
     phone_number, lead_name, first_name, last_name, taalk_lead_id, lead_email, routing_target: 'inbound609' }).
   - That JSON goes into <Enqueue><Task>...</Task></Enqueue> and is the task's attributes in TaskRouter.

3) ASSIGNMENT CALLBACK STORES IT (server/routes.ts POST /api/twilio/taskrouter/assignment)
   - When we return dequeue, we upsert into Supabase taskrouter_pending:
     reservation_sid, task_sid, worker_sid, worker_attributes, task_attributes, created_at.
   - task_attributes is the same JSON (Twilio sends it in the callback body as TaskAttributes).
   So the lead/caller data from masterlead is now in taskrouter_pending.task_attributes.

4) AGENT UI READS PENDING (client OutboundDialerInterface.tsx)
   - Every 280ms: GET /api/twilio/taskrouter/pending?agentEmail=<agent>
   - Backend (routes.ts GET /api/twilio/taskrouter/pending): reads ONLY from Supabase
     (taskrouter_injected_pending + taskrouter_pending), filters by agent (worker_attributes
     agent_email or contact_uri match). No in-memory merge — DB is the single source of truth.
   - Response: { pending: [ { reservationSid, taskSid, workerSid, workerAttributes, taskAttributes, createdAt } ] }.

5) FRONTEND BUILDS "LEAD" FOR THE PANEL (OutboundDialerInterface.tsx)
   - For the first pending item for this agent we set state: taskRouterPending = { taskSid, reservationSid, taskAttributes }.
   - inboundPanelLead is derived from taskRouterPending.taskAttributes (parse JSON):
     phone = attrs.phone_number || attrs.phone
     state = attrs.state
     market = attrs.market || 'Inbound'
     name = attrs.lead_name || [attrs.first_name, attrs.last_name].filter(Boolean).join(' ') || 'Inbound Call'
     (+ id from lead_id/taskSid, taalk_market from market).
   - That lead is passed to InboundCallHeaderPanel as prop "lead".

6) AGENT DISPLAY (InboundCallHeaderPanel.tsx)
   - Shows: clientName = lead.name (from lead_name or first_name + last_name), market badge (lead.market/taalk_market),
     and the Answer/Reject UI. So the caller name, market, phone, state that came from masterlead
     are what the agent sees.

End-to-end: masterlead row (by caller phone) → task attributes → taskrouter_pending.task_attributes →
GET pending → taskAttributes parsed to lead → InboundCallHeaderPanel shows lead name/market.

--------------------------------------------------------------------------------
WHAT'S HAPPENING WITH THE CALL (EXACT SEQUENCE)
--------------------------------------------------------------------------------
1. Caller dials 609
   → Twilio POSTs to /incomingcall (From = caller phone).

2. /incomingcall (handleIncomingCall)
   → Looks up masterlead by caller phone (last 10 digits).
   → Builds task attributes (market, state, lead_name, phone_number, etc.).
   → Returns <Enqueue workflowSid="..."><Task>attributes JSON</Task></Enqueue>.
   → Twilio answers the call, puts it in the queue, plays hold music.

3. TaskRouter
   → Creates a task with those attributes.
   → Runs workflow, finds eligible workers (market/state from Worker attributes).
   → Offers reservation to first worker → POST to assignment callback URL.

4. POST /api/twilio/taskrouter/assignment
   → Parses TaskAttributes (market, state) and WorkerAttributes (markets, licensed_states).
   → If market/state mismatch: returns { instruction: "reject" }. No DB write. TaskRouter offers to next worker.
   → If match (or no filter): builds dequeue payload (to = client:<agent_email>).
   → Puts reservation in in-memory pendingReservations (still used for accept/reject lookup).
   → Starts upsert to Supabase taskrouter_pending (reservation_sid, task_sid, worker_attributes, task_attributes, created_at) — fire-and-forget, NOT awaited.
   → Returns 200 + { instruction: "dequeue", from: DEQUEUE_FROM, to } immediately.
   → Twilio must get this response quickly; awaiting the upsert here caused routing to break.

5. Twilio (on dequeue)
   → Bridges the queued call to the worker's client (WebRTC). Caller stops hearing hold; agent's phone/client rings.

6. Frontend (OutboundDialerInterface)
   → Polls GET /api/twilio/taskrouter/pending every 280ms.
   → Backend reads ONLY from Supabase (taskrouter_pending + taskrouter_injected_pending), filters by agentEmail.
   → If a row exists for this agent: response has pending[0] with taskAttributes, createdAt.
   → Frontend sets taskRouterPending → inboundPanelState = 'ringing', builds inboundPanelLead from taskAttributes, shows InboundCallHeaderPanel (card + fuse bar).
   → Fuse: deadline = createdAt + 4s (matches TaskRouter reservation timeout).

7. Race (why card can lag by one or two polls)
   → Assignment callback returns dequeue before the Supabase upsert completes.
   → So for ~50–200ms+ the row may not be in taskrouter_pending yet.
   → GET /pending only reads Supabase, so the first poll(s) can return empty → no card until the next poll after the row appears.
   → Tradeoff: fast Twilio response (routing works) vs. possible 280–560ms delay before card/fuse appear. Demo inject writes to taskrouter_injected_pending and is available immediately, so demo feels instant.

8. Agent clicks Answer
   → incomingConn.accept() (Twilio connection) so the call actually bridges.
   → POST /api/twilio/taskrouter/accept with taskSid, reservationSid.
   → Backend accepts reservation (or no-op for demo), deletes from pendingReservations and taskrouter_pending.
   → Frontend sets dialerState.webRTCConferenceActive = true, inboundCallLead = lead, clears taskRouterPending → inboundPanelState = 'connected', card shows "Connected".

When something's wrong:
- No Enqueue? Check LIVE_CALL_INCOMINGCALL in logs; 609 Voice URL must point at /incomingcall.
- Task created but no ring? Check "TaskRouter assignment: reject (market/state mismatch)" — worker not eligible.
- Ring but no card/fuse? Row not in Supabase yet (race) or GET /pending filter (contact_uri/agent_email) not matching; check taskrouter_pending in Supabase and worker_attributes.

--------------------------------------------------------------------------------
4s BOUNCE BAR + RESERVATION TIMEOUT
--------------------------------------------------------------------------------
- Workflow reservation timeout: 4s (provision-taskrouter.ts RESERVATION_TIMEOUT_SEC=4).
  If the agent doesn't accept in 4s, TaskRouter offers to the next worker.
- UI bar that "depletes" (FuseBar in InboundCallHeaderPanel): ANSWER_DEADLINE_SECONDS=4,
  so the bar drains over 4s then next agent gets the offer (bounce).

--------------------------------------------------------------------------------
CALL CLEANUP WHEN CALL ENDS
--------------------------------------------------------------------------------
When Twilio sends call-status (status=completed, canceled, busy, or failed), we
delete from taskrouter_pending any row whose task_attributes contain that CallSid.
So when a call ends, pending reservations for that call are removed and the UI
doesn't show stale "bouncing" or ringing state.

--------------------------------------------------------------------------------
CALLER HEARS "YOUR CALL CANNOT BE COMPLETED" / CARRIER MESSAGE
--------------------------------------------------------------------------------
If the caller hears a carrier-style message (e.g. "Welcome to [carrier], your
call cannot be completed"), Twilio did not get a valid 200 + TwiML from our
Voice URL in time. Twilio typically waits ~15 seconds; then the call fails.

Causes:
1. COLD START: Server was asleep (e.g. Railway); first request took >15s.
   Fix: /incomingcall now returns INSTANT redirect (no async), so Twilio gets 200
   immediately and "answers" the call; then Twilio POSTs to /incomingcall-enqueue
   for Enqueue. Keep the service warm (cron GET /incomingcall or /health every 5 min)
   so the first request still reaches the server in time.
2. Wrong URL / TwiML App: Run check-609-voice-url.ts; 609 must point at
   .../incomingcall and have no TwiML App.
3. Server error: Check Railway logs for "📞 /incomingcall hit" and any
   errors. We always return 200 + TwiML (Enqueue or Say+Hangup) so Twilio
   should never see a 5xx from this handler.

--------------------------------------------------------------------------------
"THERE IS NO QUEUE" / CALL SHOWS BUSY OR NO ONE ANSWERS (AFTER ENQUEUE)
--------------------------------------------------------------------------------
When we return Enqueue, Twilio creates a task. The workflow sends the task to
the TaskQueue. The TaskQueue only has workers that match targetWorkers
(routing_target == "inbound609") AND are in activity AvailableInbound.
- If ZERO workers exist with routing_target "inbound609", the queue is empty.
- If workers exist but are all Offline, no one is "in" the queue.
Result: task is created but never assigned → caller hears hold then timeout →
  busy / no answer.
FIX: Create at least one worker and put them in AvailableInbound:
  npx tsx server/scripts/sync-cnsysop-inbound609.ts
  Then have that agent open the app and go Online (WebRTC). Now the queue has
  one worker; TaskRouter will offer the task to them and your assignment
  callback can dequeue the call to them.

--------------------------------------------------------------------------------
3. handleWebRTC — INBOUND FLOW (server/routes.ts, ~12812)
--------------------------------------------------------------------------------
Entry:
  - body = req.body || {}
  - callerNumber = body.From || body.from || req.query.From || ...
  - calledNumber = body.To || body.to || body.Called || ...
  - callSid = body.CallSid || body.call_sid || req.query.CallSid
  - hasConference = !!(body.conference || body.agentEmail || ...)
  - isPstnCaller = From looks like a phone number (starts with + or digits), not client:...
  - calledLast10 = last 10 digits of called number
  - shouldRouteInbound = isPstnCaller && !hasConference && (calledLast10 === '6096048379' || isInboundNumber)

If !shouldRouteInbound:
  - Log "Inbound-style request to non-inbound number ... skipping" and fall through (no return).

If shouldRouteInbound (we're treating this as inbound to 609):
  - Log "INBOUND ROUTING from ... to ..."
  - callerLast10 = last 10 digits of caller
  - is609 = (calledLast10 === '6096048379')
  - isBypassCaller = (callerLast10 === '5032018470')

  609 PATH (is609 = true):
    - effectiveCallSid = callSid || '609-fallback-' + timestamp
    - tr.isTaskRouterConfigured()? Build Enqueue (workflowSid, attrs: call_sid, phone_number, routing_target: inbound609), send TwiML, return. Else: error TwiML, return.
    - No other branch: 609 ONLY returns Enqueue or error TwiML.

  ALL OTHER INBOUND (same flow, more task attrs):
    - effectiveCallSid = callSid || 'inbound-' + timestamp
    - If tr.isTaskRouterConfigured(): optional lead lookup, buildTaskAttributesForEnqueue(...), buildEnqueueTwiML(...), res.send(enqueueTwiml), return.
    - On any error: error TwiML, return.
  So: every inbound request that reaches this handler either returns Enqueue or error TwiML. Nothing else.

  FALLBACK: USE_INBOUND_QUEUE (if not 'false') and !is609 && !isBypassCaller:
    - Puts caller in conference hold, returns hold TwiML. (609 does NOT use this because is609 is true.)

  FALLBACK: Default agents / Dial
    - Look up agent by lead or use INBOUND_DEFAULT_AGENT_EMAILS / diankablash, chrislafond, dylanwhite
    - Build Dial TwiML to client:email, return that.

CRITICAL FOR TASKROUTER TO RUN:
  - callSid must be present (from body.CallSid). If Twilio sends CallSid and body is parsed, it's there.
  - callerLast10.length >= 10 (so From must be at least 10 digits).
  - isTaskRouterConfigured() must be true: TWILIO_TASKROUTER_WORKSPACE_SID and TWILIO_TASKROUTER_WORKFLOW_INBOUND_SID (and Twilio account credentials) must be set in env or hardcoded-config.
  - Any throw between buildTaskAttributesForEnqueue and res.send(enqueueTwiml) (e.g. buildEnqueueTwiML, or pushRouteEvent) will skip the return and fall through to default agents or error.

11. POSSIBLE FAILURE POINTS (WHY NO TASK FOR A CALL)
--------------------------------------------------------------------------------
  a) REQUEST NEVER HITS THE SERVER — Twilio POSTs to Voice URL but the request never reaches baa2 (no logs, call goes busy/0s). Causes:
     - 609 number has voiceApplicationSid set: Twilio uses the TwiML App's Voice URL, not the number's. Fix: npx tsx server/scripts/set-609-voice-to-baa2.ts (clears app, sets number voiceUrl to baa2).
     - Connectivity: Twilio can't reach Railway (DNS, firewall, timeout). Check Twilio Console → Monitor → Logs → select a failed call → Webhooks: see error (e.g. connection refused, timeout, SSL).
     - Verify: npx tsx server/scripts/check-609-voice-url.ts shows "URL Twilio will POST to" = baa2 and no TwiML App.
  b) callSid missing in req.body — e.g. Twilio sent GET instead of POST, or body not parsed. Unlikely if Twilio is configured to POST.
  c) callerLast10.length < 10 — From number too short. Unlikely for normal callers.
  d) isTaskRouterConfigured() false on the server that received the request (e.g. baa2 missing env TWILIO_TASKROUTER_WORKSPACE_SID or TWILIO_TASKROUTER_WORKFLOW_INBOUND_SID). Then we skip Enqueue and fall through to default agents Dial.
  e) Exception inside the TaskRouter block (e.g. buildTaskAttributesForEnqueue, buildEnqueueTwiML, or pushRouteEvent). The try/catch around the lead lookup does not wrap the whole block; only the lead lookup is in try/catch. So if tr.buildTaskAttributesForEnqueue(...) or tr.getWorkflowSidForEnqueue() or tr.buildEnqueueTwiML(...) throws, the error propagates and handleWebRTC may send an error or fall through.
  f) Different server instance: Voice URL hits baa2 but baa2 has different env (e.g. TaskRouter not configured there). Then baa2 would not return Enqueue.
  g) Task created but with attributes that don't match: e.g. call_sid stored under a different key. check-call-taskrouter.ts looks for task.attributes.call_sid === callSid. If the attribute key were different, we wouldn't find the task.
